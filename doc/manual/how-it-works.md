# How it works

The mod has two parts. One decides which strings in a save are display text. The other finds each string's entry in the game's tables and replaces it with the same entry in the target language.

## Matching text

Each source-language string is looked up in the game's string tables and replaced with the entry of the same id in the target language. The matcher handles:

- exact entries;
- smart-format templates such as `Durability: {0}/{1}`, with their arguments translated recursively;
- text the game concatenated from several entries, such as `Music Cassette - ` + `Stardust` + ` (Corrupted)`;
- multi-line notes built from several entries;
- fixed suffixes the game appends, such as `(99%-99.9% Purity)`.

When several entries share a source string, the entry whose key shares words with the ids next to the text wins. For example `plant_trait_unappetizing_name` wins next to `category: plant_taste`. Entries whose key says `plural` lose. After that, the more central table wins, then the most common translation, then the shorter text.

The matcher lives in `src/Translator.Pure.cs`.

## Choosing what to convert

`src/SaveWalker.cs` walks the save and hands every string to `src/TextPolicy.Pure.cs`, which decides what is display text. Non-ASCII text is converted in any field that is not an id or a known internal field such as a file name or a seed. ASCII text is converted only in fields the game is known to localize. The allow-list was found by comparing a Chinese save with the tables. Fields such as `subtitle` hold English even in a Chinese save. They are internal names and stay unchanged. A few fields, such as `displayName`, hold two kinds of text. People's names stay in English in the game. The names of night services and events appear in the player's language. In these fields English text is replaced only when it is exactly one game entry and not a person's name. A person is recognised by the `name_` id stored next to the name.

The save classes the walker may visit are listed in `src/KnownTypes.g.cs`, generated by `tools/Closure.cs` from the game DLL.

## Performance

How each step grows with the size of a save, and what the speedups changed. L is the length of the save text, S the number of strings in it, E the number of strings that change, and T the number of templates in the source language (693 for English).

Rewriting the save. The rewriter used to replace each changed string in place in one buffer. Every replacement shifted the rest of the save, so a conversion cost O(E·L). It now records the replacements during one walk, then copies the save once: the unchanged slices and the replacements, in order. That costs O(L + E). On a 13 MB save with about 4,200 changes the rewrite went from about 3 s to 0.35 s, and the output is byte for byte the same. In the game a whole conversion, building the tables included, takes about 0.55 s.

Deciding which fields hold ids. The answer for a field name is worked out once and remembered, so each string costs one hash lookup instead of running the rules again.

Matching one string of length n:

- An exact entry is one hash lookup, O(n).
- Text without nearby context is remembered after its first match, so each distinct text is matched once per conversion.
- Templates are tried one after another, O(T·n) at worst. A template whose fixed text does not occur in the string is skipped before its pattern runs, so most are ruled out by one substring search.
- Text concatenated from several entries is split by a shortest segmentation over pieces of up to 80 characters. That is O(80·n) dictionary lookups. It is only tried for strings of up to 160 characters, and the result may use at most 6 entries.
- Multi-line text tries runs of consecutive lines, O(m²) lookups for m lines.

## Tests

The engine is kept apart from the game and Unity in `src/*.Pure.cs`, which use nothing but plain C#: the matcher in `Translator.Pure.cs`, the field rules in `TextPolicy.Pure.cs` and the save rewriter in `JsonText.Pure.cs`. The code that talks to the game only reads the string tables and the loaded save and passes them on.

`tests/run.sh` runs `tests/PureTest.cs`, which checks the engine on hand-made table entries without the game, Unity or a save: exact entries, templates and their arguments, choosing between entries that share a source string, untranslated text, and rewriting JSON in place. With the game installed it also runs the mod scanner.

`tests/EngineTest.cs` runs the engine outside the game, on string tables exported from the game's bundles and on a real save. For the Chinese save the engine was developed with:

- Chinese to English: 492 of 492 distinct texts match a hand-checked conversion, and 60,719 of 60,721 strings in the whole save are identical. The 2 differences are intentional: sprite bookkeeping is left alone, and `startLocale` is set by the mod.
- English to Chinese: no Chinese text is lost. The differences are one-to-many cases, where one English line has several Chinese ones, and English names the game also keeps in Chinese saves.

`tests/ScanTest.cs` runs the game's own mod scanner on the built DLL. The result is no capabilities and not refused.
